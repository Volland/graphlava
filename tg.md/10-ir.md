# Shared IR

The extended-Datalog intermediate representation that SPARQL 1.2, Cypher and the Datalog surface all compile to: relations over u64 tuples, operators, execution modes and virtual relations.

- follows_from:: [[adr:0013]]
- follows_from:: [[adr:0014]]
- depends_on:: [[02-id-encoding#Bit layout]] {strength: hard}
- depends_on:: [[01-data-model#Statements]] {strength: hard}

## Purpose

One IR means one planner, one executor and one place for optimisations. Front ends translate syntax and semantics flags; they never execute anything themselves.

Every value in the IR is a `u64` ID ([[02-id-encoding#Bit layout]]) or the null ID `0`. Strings are decoded only by the final `Project` operator (late materialisation). A program is a set of rules plus one query rule; non-recursive queries are a single stratum.

<non-goal>

The IR is not a user-facing language and has no stable textual syntax in v0. A debug pretty-printer exists; it may change between releases.

</non-goal>

## Relations

The IR names three kinds of relation: stored, virtual and derived. The planner sees them through one interface and picks access paths from their declared orderings.

| Kind | Examples | Access paths |
| --- | --- | --- |
| Stored | `triple(s,p,o,id)` over SPO/POS/OSP plus any on-demand ordering | prefix scans of each existing ordering |
| Virtual | `prop`, `reifies`, `role`, `in`, `in_star`, `hedge_T` | computed from tables, see [[10-ir#Virtual relations]] |
| Derived | heads of `@materialized` rules, `in_star` | derived table ([[13-datalog#Materialized maintenance]]) |
| Transient | heads of `@on_demand` rules, subquery results | in-memory, per query |

<rule id="ir-tuple-u64" strength="must">

Every column of every relation is a `u64`. Column 0 of the null ID means unbound. No operator other than `Project` and `Filter` with a decoding builtin may look at a term's string form.

</rule>

<rule id="ir-statement-relation" strength="must">

The base relation is `triple(s, p, o, id)`. Because `(s,p,o)` is unique for non-multi predicates ([[adr:0004]]), `id` is functionally determined by `(s,p,o)` and the planner may treat it as a value, not a join column. For `multi` predicates the relation is a bag keyed by `id`.

</rule>

## Operators

The logical operator set. Each operator consumes and produces batches of u64 tuples; the physical choice (merge, hash, Leapfrog) belongs to [[14-planner-execution#Join selection]].

| Operator | Meaning | Notes |
| --- | --- | --- |
| `Scan(rel, bound, order)` | read a relation with some columns bound | chooses an ordering whose prefix covers `bound` |
| `Join(inputs, vars)` | natural join on shared variables | n-ary; Leapfrog Triejoin for cyclic shapes |
| `LeftJoin(l, r, cond)` | keep `l` rows without a match, unbound columns = 0 | SPARQL `OPTIONAL`, Cypher `OPTIONAL MATCH` |
| `AntiJoin(l, r)` | rows of `l` with no match in `r` | stratified negation, SPARQL `MINUS` / `FILTER NOT EXISTS` |
| `Union(inputs)` | bag or set union by mode | |
| `Filter(expr)` | keep rows where `expr` is true | three-valued per front-end flags |
| `Extend(var, expr)` | add a computed column | SPARQL `BIND`, Cypher computed `WITH` |
| `Aggregate(groups, aggs)` | group and aggregate | `COUNT`, `SUM`, `MIN`, `MAX`, `AVG`, `SAMPLE`, `GROUP_CONCAT`, `collect` |
| `Distinct` | set semantics | inserted by the mode rules |
| `OrderBy`, `Slice` | sort, `LIMIT`/`OFFSET` | top-k fused when possible |
| `Fixpoint(rules)` | semi-naive recursion | property paths, variable-length paths, recursive rules |
| `Path(start, pred_expr, end, min, max)` | regular path over predicates | BFS kernel when an end is bound, `Fixpoint` otherwise ([[14-planner-execution#Path evaluation]]) |
| `Service(iri, sub_plan)` | delegate to a `ServiceResolver` | `<meta:datalog>` is local ([[11-sparql#Datalog service]]) |
| `VectorSearch(index, query_vec, k, filter)` | top-k nearest IDs with scores | [[15-vector-index#IR operator]] |
| `Project(vars, decode)` | final columns, decode IDs to terms | the only decoding point |
| `Write(ops)` | insert, delete, update-in-place | update queries only, see [[10-ir#Operators#Write operators]] |

<rule id="ir-join-nary" strength="must">

`Join` is n-ary in the IR. The planner, not the front end, decides between binary hash or merge joins and a multiway Leapfrog Triejoin (Veldhuizen, "Leapfrog Triejoin: a simple, worst-case optimal join algorithm", ICDT 2014).

</rule>

<rule id="ir-leftjoin-scope" strength="must">

`LeftJoin` carries its filter condition inside the operator, so SPARQL's `OPTIONAL { … FILTER(…) }` keeps its scoping and is never rewritten to a `Filter` above the join.

</rule>

### Write operators

Update requests compile to `Write` nodes that run inside one writer transaction, after the read part of the plan has produced its bindings.

| Write op | Arguments | Effect |
| --- | --- | --- |
| `Insert(s,p,o)` | three IDs or bindings | if `(s,p,o)` exists and `p` is not multi, adds a membership of the target graph or does nothing ([[09-graphs#Membership operations]]); on a `functional` predicate, updates the existing statement in place |
| `Delete(s,p,o)` | three IDs | cascades to annotations ([[06-transactions-durability#Cascade delete]]) |
| `UpdateInPlace(id, o'[, expected])` | statement ID, new object, optional expected current object | keeps the ID; with `expected`, fails with `Conflict` on mismatch; see [[11-sparql#Reifiers]] |
| `SetProp(n, p, v)` / `DelProp(n, p)` | node, predicate, literal | inline property overwrite |
| `CreateHedge(T, roles)` / `DeleteHedge(e, detach)` | type, role bindings | [[08-hyperedges#Record format]] |
| `AddMember(x, g)` / `RemoveMember(x, g)` | item and graph | [[09-graphs#Extra membership]] |
| `DropGraph(g, recursive)` | graph | [[09-graphs#Graph drop]] |

<rule id="ir-write-after-read" strength="must">

All `Write` ops of one request see the snapshot taken before any of them ran (SPARQL Update semantics). Their effects are applied in the order delete-then-insert, and a delete plus insert on the same `(s,p)` with the same reifier collapses to one `UpdateInPlace`.

</rule>

## Modes

Per-query and per-operator flags that let one IR carry SPARQL, Cypher and Datalog semantics without separate operators.

| Flag | Values | Default by front end |
| --- | --- | --- |
| `multiplicity` | `bag`, `set` | SPARQL `bag` (`set` under `DISTINCT`), Cypher `bag`, Datalog `set` |
| `edge_iso` | `off`, `on` | Cypher `on` within one `MATCH`, others `off` |
| `null_semantics` | `sparql_unbound`, `cypher_null`, `datalog_none` | per front end |
| `type_errors` | `filter_false`, `raise`, `null` | SPARQL `filter_false`, Cypher `null`, Datalog `raise` |
| `graph_scope` | `transitive`, `direct` | SPARQL `transitive` ([[adr:0007]]), `direct` in the conformance mode |
| `compare` | `rdf_term`, `cypher_value` | ordering and equality rules for mixed types |

<rule id="ir-edge-iso" strength="must">

When `edge_iso` is `on`, the executor rejects any row that binds the same statement ID to two relationship variables of one pattern. This is implemented as a pairwise inequality filter on statement-ID columns, pushed into the join as early as both columns are bound. It is designed in v0 and first used by Cypher in v1.

</rule>

<rule id="ir-mode-explicit" strength="must">

Every operator carries its resolved modes. The optimiser may only rewrite between operators with the same modes, or with a rule that is proven safe for both (for example, `Distinct` above a `set` input is removed).

</rule>

<example>

<input>

SPARQL `SELECT ?x WHERE { ?x :knows ?y . OPTIONAL { ?y :age ?a } FILTER(!BOUND(?a)) }`

</input>

<output>

`Project([x], Filter(is_null(a), LeftJoin(Scan(triple, p=:knows), Scan(prop, p=:age), true)))` with `multiplicity=bag`, `null_semantics=sparql_unbound`.

</output>

</example>

## Virtual relations

Relations that look like triples to the query layer but are served from other tables. The planner knows their cost and their access paths and never materialises them.

| Relation | Columns | Served from | Bound-column access paths |
| --- | --- | --- | --- |
| `prop(n, p, v, id)` | node, predicate, literal value, statement ID or 0 | `props` record; promoted entries via pointer | `n` bound: one record read; `p` bound: `plist` range, then one record read per node; `p` and a value or range bound: `propidx` range if indexed, else as `p` bound with a filter |
| `reifies(r, s, p, o)` | reifier, triple term | `stmt[id]` with `r = id` | `r` bound: one lookup; `s,p,o` bound: ordering lookup returns `id` |
| `role(e, role, n)` | hyperedge, role IRI, node | `hedge` record and `incidence` | `e` bound: record; `n` bound: incidence prefix |
| `hedge_T(e, r1..rk)` | one column per role of type `T` | `hedge` record, type chunks | type scan as chunk ranges ([[08-hyperedges#Star-pattern collapse]]) |
| `in(x, g)` | item, graph (direct) | `gchunk` by chunk of `x`, plus `gmem` | `x` bound: one lookup; `g` bound: chunk ranges plus `gmem_rev` |
| `in_star(x, g)` | item, ancestor graph | `in` joined with the `in_star` graph closure | `g` bound: union of descendant ranges ([[09-graphs#Scope expansion]]) |
| `derived(s, p, o)` | materialised rule heads | derived table | prefix scans as for `triple` |

<rule id="ir-virtual-triple-union" strength="must">

A triple pattern with an unbound or literal-valued predicate compiles to a `Union` of `Scan(triple)` and `Scan(prop)`, and of `Scan(derived)` when a materialised rule may produce that predicate. A pattern whose predicate is bound and known (from the meta-model or stats) to be only node-valued, only literal-valued or only derived reads one source.

</rule>

<rule id="ir-reifies-virtual" strength="must">

`rdf:reifies` is never stored. A pattern `?r rdf:reifies <<( ?s ?p ?o )>>` compiles to `Scan(triple)` binding `id` as `?r`, so a reifier costs zero extra joins.

</rule>

<rule id="ir-membership-lazy" strength="must">

`in(x, g)` has no statement ID column unless the membership is promoted ([[adr:0017]]). A query that binds the reifier of a membership triple joins with the promoted-membership pointer and gets no row for unpromoted memberships.

</rule>

## Builtins

Functions callable from `Filter` and `Extend`. They operate on IDs where possible: comparisons on inline literals are integer comparisons, and only string builtins decode.

<rule id="ir-builtin-inline-compare" strength="must">

Comparisons (`<`, `<=`, `=`, `>=`, `>`) between two inline literals of the same subtype are integer comparisons on the ID ([[02-id-encoding#Inline literals]]). Any other comparison decodes both sides and applies the front end's `compare` mode.

</rule>

Callable Datalog predicates appear as `Scan` of an `@on_demand` rule head with bound-argument adornments; magic sets are applied before planning ([[13-datalog#On-demand evaluation]]).

## Failure behaviour

How the IR layer reports errors. Compilation errors never reach the executor; runtime errors abort the query and, for updates, roll back the transaction.

<rule id="ir-errors" strength="must">

Unknown predicates or rule names, unsafe rules (a head variable not bound by a positive body atom) and unstratifiable negation are compile errors. Type errors at runtime follow the `type_errors` mode. Resource limits (row budget, time budget, recursion depth) abort the query with a typed error that names the operator.

</rule>

## Test plan

How the IR is tested independently of the front ends: round-trips, semantic equivalence between front ends and property tests of each operator against a naive reference executor.

- Golden tests: each front end compiles a corpus of queries; the IR pretty-print is compared with a stored snapshot.
- Reference executor: a slow, obviously correct nested-loop executor over in-memory tuples; random IR plans are checked against the real executor (differential testing).
- Mode tests: one table of queries per flag value (bag vs set, edge_iso, null semantics, graph scope) with expected results.
- Virtual relations: for random stores, `Scan(prop)` and `Scan(triple)` results equal those of a store where every property is a full statement.
- Benchmark: [[17-benchmarks#Ordering count comparison]] covers the plans that the three-ordering layout makes slower.

## Open items

Questions this spec leaves open; each is an `OpenQuestion` in the open-questions file.

- [[open-questions#IR textual syntax]]: whether the IR gets a stable text form (for plan caching on disk, debugging, and tests).
- [[open-questions#Cypher null and comparison semantics]]: how far `cypher_value` comparison and three-valued logic are emulated over RDF terms.
- [[open-questions#Unbound predicate cost]]: whether patterns with an unbound predicate must union three sources or a per-node predicate summary can prune them.
