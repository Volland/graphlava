# Design

## Context

Swift and Kotlin cannot use a Rust-native binder the way PyO3 and napi-rs do, so they reach the core through one stable C ABI ([[16-api#C FFI]], [[adr:0042]]). Mobile operating systems also decide when an app runs:

- iOS suspends an app seconds after it goes to the background. It kills the app with `0xdead10cc` if the app still holds a lock on a file in an app-group container.
- Android kills background processes without warning.
- App extensions run as separate processes and must not open the database file ([[adr:0002]]).

## Decisions

### D1. Hand-written Swift and Kotlin over the cbindgen C header ([[adr:0042]])

- **Choice:** the C API in `graphlava-ffi`, with a header generated by cbindgen. Swift imports it through a module map in the XCFramework. Kotlin calls it through a thin JNI shim compiled into the same `.so`.
- **Rejected:**
  - UniFFI. It generates idiomatic code, but it would put a second ABI next to the C ABI, and its lifecycle hooks cannot place `graphlava_suspend` inside `beginBackgroundTask`.
  - Kotlin/Native cinterop. It does not run on the Android JVM.
- **Reasons:** `motivated_by` `api-ffi-abi`. One frozen ABI also serves C, Go and .NET callers.

### D2. Suspend is a core operation; lifecycle wiring lives in the bindings

- **Choice:** `graphlava_suspend` does the following in order:
  1. It aborts the open interactive write. One-shot requests already in the batch commit.
  2. It flushes the group-commit batch.
  3. It ends the snapshots.
  4. If the file is in an app-group container, it releases the lock.

  `graphlava_resume` reacquires the lock and reopens snapshots lazily. Calls made while suspended wait for resume. Swift calls suspend inside `beginBackgroundTask`, and Kotlin flushes on `ON_STOP` without releasing the lock.
- **Rejected:**
  - Closing and reopening the database. This loses the plan cache and the statistics, and costs a full open.
  - Committing the interactive write on suspend. Its caller has not finished it.
- **Reasons:** `motivated_by` `api-ios-suspend`, [[07-platforms#iOS]] and [[07-platforms#Android]].

### D3. Threading: an actor in Swift, dispatchers in Kotlin

- **Choice:**
  - Swift's `Database` is an `actor` backed by a serial executor on one dedicated thread. Reads fan out to a bounded task group.
  - Kotlin uses a single-thread write dispatcher and a read pool sized to the core count. Debug builds throw on main-thread calls.
- **Rejected:** a synchronous API, which blocks the main thread and causes ANRs on Android.
- **Reasons:** `motivated_by` `api-kotlin-threads` and `api-no-async-required`.

### D4. iOS extension writes through XPC or a journal (ADR 0043)

- **Choice:**
  - `ExtensionClient` sends requests over XPC when the app is running.
  - Otherwise it appends frames to `<appgroup>/graphlava/<extension-id>.journal`. Each frame is `len:u32le | seq:u64le | crc32c:u32le | WriteRequest bytes`.
  - The framing, CRC-32C, sequence numbering and apply logic live in the C FFI (`graphlava_journal_append`, `graphlava_journal_apply`, `crates/graphlava-ffi/src/journal.rs`), so every binding shares one tested implementation; `ExtensionClient` calls them. The file starts with a 16-byte header (`GLVJ`, version 1, base sequence number) that truncation rewrites, so sequence numbers are never reused.
- On open, the owner applies each frame as one write request. It writes `journal_seq[<extension-id>] = seq` in the same transaction, so each frame is applied exactly once.
  - A torn tail (bad length or bad CRC) is dropped with one warning.
  - The journal is truncated after it has been fully applied.
- **Rejected:**
  - Failing the write, so extensions lose data.
  - Opening the file from the extension, which risks `0xdead10cc` and breaks [[adr:0002]].
  - One journal shared by all extensions, which needs a cross-process lock on the journal.
- **Reasons:** resolves [[open-questions#Extension write queue]]. `motivated_by` `api-ios-extension-ipc` and [[07-platforms#iOS]].

### D5. Native IDs and errors

- **Choice:** Swift uses `UInt64` IDs and a `GraphLavaError` enum with associated values. Kotlin uses `ULong` IDs and a sealed `GraphLavaException` hierarchy. Both map one-to-one from `graphlava_status` codes.
- **Rejected:** signed `Int64`/`Long`, which turns every tagged ID negative.
- **Reasons:** `motivated_by` [[02-id-encoding#Bit layout]].

## Formal model

No Lean changes. Suspend reuses the durable-prefix theorem in `MetaCore.Durability`: suspend is a commit boundary followed by closing the snapshots. New `<assumption>` entries for `tg.md/20-proofs.md`:

- `graphlava_suspend` leaves no partially applied transaction.
- A journal frame's write request and its `journal_seq` update commit in one transaction.

## Refinement

The abstraction function is the identity on public API state. The Swift package replays oracle traces (seeds 1..8 × 2,000) on the macOS host. Kotlin replays the same traces as JVM unit tests against the host `.so`. Both run the shared conformance corpus. The journal has its own small model: the applied set equals the prefix of complete frames. Torn-tail fuzzing checks it against that model.

Crash points:
- During `graphlava_suspend`, between the flush and the lock release.
- Between journal frames while they are applied.
- Midway through appending a journal frame.
- After `ON_STOP` on Android.

## Cost model

- `graphlava_suspend` costs one group-commit flush (one `fsync` or `F_FULLFSYNC`), plus O(open snapshots) to close them. When the last commits were `relaxed`, the flush is a durable empty commit. Releasing the lock of an app-group file also drops the redb handle, which writes its allocator state with one more flush; a private-container suspend with nothing open takes microseconds.
- Snapshots must end before the lock is released. The FFI ends the snapshots of its result and read handles itself; a Rust `ReadTxn` still open after a 1 s wait makes suspend fail with `Error::Busy` (`GRAPHLAVA_ERR_BUSY`), leaving the database suspended with the lock held.
- `graphlava_resume` costs one lock acquire. Snapshots reopen lazily.
- Applying the journal costs one `WriteRequest` and one metadata-key write per frame. Each frame commits `ordered` (a durable commit each) so a kill midway never re-applies a frame; the final flush precedes truncation.
- The FFI adds one fixed overhead per call and one per decoded term. Batches cross one per 1024 rows.

## Benchmarks

[[17-benchmarks#Mobile]], extended:

- **Workload:** the agent-memory mix subset.
- **Datasets:** 1M and 10M statements, seed 42, `ordered` durability.
- **Devices:** one reference iPhone and one reference Android arm64 device.
- **Metrics:** p50 and p99 latency, file size, energy per 10^4 operations where available, and suspend and resume time in ms.
- **Pass line:** suspend p99 below 500 ms at 10M statements. Every other metric is to be measured.

`Binding overhead` runs the FFI on the Linux host runner.

## Failure model

- A throwing Swift closure, or a cancelled Kotlin coroutine, aborts the transaction.
- A panic becomes `GRAPHLAVA_ERR_INTERNAL`, and Swift and Kotlin surface it as an internal error.
- A kill during suspension keeps every acknowledged commit, because suspend flushes before releasing the lock.
- A torn journal tail is dropped. Complete frames are applied exactly once, even across a crash during apply.

## Risks / Trade-offs

- [The iOS background window may be shorter than the flush at 10M statements] → the 500 ms gate, plus abort-instead-of-commit for an open interactive write.
- [XPC needs entitlements and a Mach service] → the journal path works without XPC; XPC is an optimisation.
- [Device CI is slow and flaky] → the simulator and emulator run on every PR, and the device crash tests run nightly.
- [The JNI shim is hand-written C] → the shim is a thin forward over the header, compiled with `-Wall -Werror` for the host and both Android ABIs, and exercised by the JVM host tests; the fuzzing target covers the C API beneath it.
- [Handles are raw pointers] → handles are registry tokens, so use after close, double commit and wrong handle kinds return statuses instead of undefined behaviour.
