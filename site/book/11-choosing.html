Is a property graph enough?

Many projects reach for a metagraph too early. A labelled property graph is enough when all of these hold:

  • Relations are binary, or have a small fixed set of extra values.
  • Edge properties are values, never links to other nodes or edges.
  • Nobody asks "who said so?" or "how sure are we?" about an edge.
  • The data has one perspective: no episodes, sources or agents that disagree.

You need a metagraph when any of these holds:

  • Relationships have relationships ("the meeting led to the price change").
  • The same fact is held with different confidence by different sources.
  • Knowledge is grouped into episodes, documents or projects that are themselves described.
  • Rules or the schema must be queried and changed like data.

Agent memory usually meets the second list on the first day: every remembered fact has a source and a confidence.

Five rules of thumb

  1. Climb only as far as the problem needs. A binary fact that is never annotated costs the least, and graphlava is designed so that it pays for nothing else.
  2. Give a relation a type when its roles are fixed. The store can then check it and read it as one record.
  3. Annotate instead of encoding. A confidence belongs on the statement, not in a compound predicate or a side table.
  4. Point dependencies the way deletes flow. Annotations follow their subject into deletion. A reference from the object position does not cascade; it blocks the delete unless DETACH (ADR 0036).
  5. Group with graphs, not with properties. A :context value on every fact cannot be nested, scoped or described. A graph can.

Closing

The book started with a meeting that binary edges could not hold, and ended with a memory where a fact, its source, the source's checker, the meeting, its outcome, the episode and the rule that reads them all are statements in one ID space. Nothing in between needed a second data model. That is the case for statement graphs as the ground floor of a metagraph store: give every statement an identity, let identities stand where nodes stand, and the higher rungs of the ladder become ordinary writes.

graphlava is designed around that idea, with the physical choices that agent memory asks for: IDs given lazily, overwrites that cost one write, hyperedges stored once, and scopes that cost in proportion to the graph. The specs are in the repository.

In graphlava. Every row of the table above maps to a part of the spec: statements and promotion (data model), hyperedge records (hyperedges), membership and scope (graphs), the system graph (meta-model) and Datalog (rules). One query core, SPARQL 1.2 and Datalog in v0, reads all of it.

Takeaways

  • Pick the lowest rung that holds the problem; graphlava charges for higher rungs only where they are used.
  • Fixed roles: hyperedge type. Remarks: annotation. Groups: graphs. Conclusions: rules. Schema: the system graph.
  • Choose tiramemsu when the memory must remember its own past.
